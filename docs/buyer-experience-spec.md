# LOCAL AI OS — buyer journey and interactive demonstration contract

**Revision:** 2026-11-20. **Audience:** prospective technical buyer, founder and product reviewer. **Status:** product copy and synthetic public UI; not evidence of a live customer install.

## The job we sell now

An engineer with a private Linux workstation repeatedly wastes time rebuilding project context, re-explaining architecture to AI and verifying whether AI-produced work is really complete. LOCAL AI OS is currently a **productized founder-led implementation service**: it makes one expensive repeated workflow documented, scoped, observable, testable and recoverable.

It is **not** the complete private System sold as a self-service agent platform. Do not imply SaaS tenants, user accounts, cloud synchronization, universal Codex/ChatGPT access, automatic merge or unrestricted AI action.

## Visitor journey

1. See one concrete failure: context drift, unapproved scope or false «done».
2. Read what the local-first, proof-first workflow changes. Make the first screenshot show an observable workbench, not 11 abstract technical layers.
3. Try \`/demo\` without signup: choose resume / defect / privacy and walk across six workflow stages.
4. Deliberately request out-of-scope execution: observe a **simulated** policy denial rather than fake success.
5. Request simulation verification, inspect the simulated report and see that actual deployment and business value remain **unverified**.
6. Inspect published founder proof. Its 12 verified runs and 17 context-preflight runs are aggregate founder telemetry, **not** matched uplift, external customer outcomes or proof that the demo executed anything.
7. Open \`/value\`: see specific paid deliverables, limits and an editable **hypothetical** context-loss cost calculator; no ROI promise.
8. Open \`/compare\`: see overlaps with alternatives, official references and the comparative test plan.
9. Open \`/architecture\`, \`/system-architecture\`, \`/acceptance\` and \`/security\` for technical due diligence.
10. Apply for a founder-led diagnostic via the pre-existing Telegram channel; no new checkout, CRM, user store or external-tracking stack.

## Six demonstration phases

- **Intent:** defined job and objective, not arbitrary AI output.
- **Context:** synthetic examples of canonical/source/continuity selection; excluded data stays visible as excluded.
- **Authority:** switch between allowlisted action and attempted forbidden action; denial prevents a positive conclusion.
- **Execution:** static simulated trace; the browser **never executes a command** or calls a model.
- **Verification:** explicit visitor action to evaluate example; outcome remains pending until this action; forbidden requests are blocked.
- **Handoff:** truthful status, next action and explicit statement that deployment and real benefit have not been measured.

Reset clears the demo verification and simulated violation. Changing the use case or permission choice invalidates the previous simulated verification. The page neither reads external repositories nor uploads visitor input or sends prompts. Synthetic source labels must never resemble actual private paths or customer data.

## Direct access and accessibility

The Vite/GitHub Pages build must emit index artifacts for \`/demo\`, \`/value\` and \`/compare\`, not just a SPA path. Text and controls must be keyboard accessible; scenario and permission buttons use \`aria-pressed\`, active step uses \`aria-current\`, output uses an \`aria-live\` region, layout adapts at desktop/tablet/mobile widths, reduced-motion preference is honored.

## Acceptance: what QA can and cannot prove

\`npm run check:demo\` checks routes, critical controls, safety disclosures and the absence of runtime network APIs in the demo source. \`npm run qa\` also runs existing build, proof, offer, documentation, static-route and security checks. These are source/CI-level gates. A live visual and keyboard check at desktop and mobile widths, exact-commit GitHub Pages deploy verification, and an actual client diagnostic require separate evidence.

## Do not fabricate value

The calculator computes hypothetical baseline exposure from visitor-provided minutes/week and hourly cost: \`minutes / 60 * hourlyRate * 4.33\`. It does not predict time savings or revenue. Any claim of measured improvement requires a paired baseline, accepted outcome, comparable environment and cost accounting. Synthetic demo telemetry must never feed public proof metrics.
